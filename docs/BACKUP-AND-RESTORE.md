# النسخ الاحتياطي والاستعادة

> **حالة الوثيقة:** OPEN-10 **محسوم**. السياسة كاملة في §٦، والآلية التي
> تُنفّذها في §٧.
> نجاح تمرين الاستعادة أحد شرطي الخروج من المرحلة P8، وقد **نُفِّذ فعلاً** —
> النتائج في §٤.

---

## ١. ما الذي يُنسَخ، ولماذا ثلاثة ملفات لا ملف واحد

```bash
npm run backup                 # إلى ./backups بالافتراض
npm run backup -- /srv/backups # أو إلى مسار محدَّد
```

كل نسخة مجلّد مختوم بالتوقيت يحوي أربعة ملفات:

| الملف | ما هو | لماذا لا يكفي بدونه |
|---|---|---|
| `roles.sql` | أدوار العنقود | **نموذج الصلاحيات كلّه** سياسات RLS معلّقة على `app_user` و`migrator`. استعادة قاعدة بيانات في عنقود لا يحوي هذين الدورين تفشل، أو — وهو أسوأ — تنجح وتترك جداول تشير سياساتها إلى دور غير موجود |
| `database.dump` | القاعدة بصيغة PostgreSQL الخاصة | الصيغة الخاصة تتيح استعادة متوازية وانتقائية |
| `manifest.json` | **حالة الدفاتر لحظة أخذ النسخة** | بدونه لا يمكن إثبات أن ما استُعيد هو *نفس* الدفتر. انظر §٣ |
| `SHA256SUMS` | بصمات الملفات الثلاثة | ليُكتشف التلف **قبل** محاولة الاستعادة لا أثناءها |

`roles.sql` يُؤخذ بـ`--no-role-passwords`: بصمات كلمات المرور غير لازمة
لاستعادة البنية، والنسخة الاحتياطية تُنسخ إلى أماكن أكثر مما تُنسخ إليه قاعدة
البيانات.

### ما **لا** يُنسَخ هنا

**ملفات المنتجات الأصلية والمعاينات.** تعيش في تخزين كائنات متوافق مع S3،
منفصل عن خادم التطبيق — وهذا قرار المالك على OPEN-10، وهو الوضع القائم منذ P3:
لا يوجد في المشروع دلو عام، ولا مسار يقرأ ملفاً أصلياً من قرص الخادم. نسخها عبر
هذا السكربت بطيء وخاطئ معاً؛ تكرارها مسؤولية مزوّد التخزين، ويُفعَّل عنده
Versioning حتى لا يمحو رفعٌ خاطئ نسخةً سليمة.

---

## ٢. متى تُؤخذ النسخة

`manifest.json` يُقرأ **بعد** انتهاء الـdump عن قصد. إن رُحِّلت معاملة مالية بين
الاثنين، سجّل البيان رأس سلسلة لا تحويه النسخة، و**يفشل التمرين بصوت عالٍ** —
وهي النتيجة الصحيحة: نسخة أُخذت أثناء كتابة ليست نسخة تُوثَق بها بصمت.

**لذلك:** خذ النسخة من لحظة هادئة، أو — الأفضل للإنتاج — من نسخة قراءة
(replica).

## ٣. تمرين الاستعادة

```bash
npm run restore-drill                  # أحدث نسخة في ./backups
npm run restore-drill -- /srv/backups/20260912T220308Z
KEEP=1 npm run restore-drill           # أبقِ قاعدة التمرين للفحص اليدوي
```

يستعيد إلى قاعدة بيانات مؤقتة ثم يسأل **مجموعتين** من الأسئلة. المجموعتان
ضروريتان معاً، وهذا ليس ترفاً — انظر البرهان في §٤:

**الهوية — هل هذا *نفس* الدفتر؟** كل عدّاد، ورأس سلسلة التجزئة، يُقارَن ببيان
النسخة. بدون هذه المجموعة يكون التمرين شبه عديم القيمة: **قاعدة بيانات فارغة
تماماً تجتاز كل فحص اتساق موجود.**

**السلامة — هل الدفاتر المستعادة سليمة؟** تُعاد سلسلة التجزئة من أول قيد،
وتُجمع كل السطور، ويُعدّ نموذج الأمان. وتُسأل هذه الأسئلة للقاعدة **المستعادة**
عبر دوالّها هي، فاستعادةٌ فقدت دالّة أو سياسة تفشل هنا.

أقوى فحص مفرد في السكربت هو **رأس السلسلة**: تجزئة الرأس تلتزم بكل قيد قبلها،
فتطابقها يعني أن لا قيداً ضاع ولا أُضيف ولا عُدِّل في أي موضع من السلسلة.

## ٤. التمرين المُنفَّذ — النتائج

### ٤-١ نسخة سليمة: ٢٢ فحصاً، كلها ناجحة

```
1. THE BACKUP ITSELF            3/3
2. RESTORE                      4/4   app_user still cannot bypass RLS — f
3. IDENTITY                    10/10  hash-chain head entry hash — 9e8fc9b0…
4. INTEGRITY                    2/2   chain re-verifies: 0 problems
                                      every currency sums to zero
5. THE SECURITY MODEL           3/3   70 policies, 31 RLS tables, 20 SECDEF
DRILL PASSED
```

### ٤-٢ البرهان أن التمرين يكشف فعلاً — عطبان مصنوعان عمداً

حارسٌ لم يُشاهَد وهو يفشل ليس حارساً. لذلك أُعدّت نسختان معطوبتان:

**العطب الأول — تعديل سطر واحد في الدفتر بمقدار ١٠٠ وحدة صغرى:**

| المجموعة | النتيجة |
|---|---|
| الهوية | **نجحت كلها** — العدّادات ورأس السلسلة لا يتغيّران بتعديل محتوى |
| السلامة | **فشلت**: مشكلتان في السلسلة، وعملة واحدة لا تساوي صفراً |

**العطب الثاني — ضياع آخر معاملة في الدفتر كاملة:**

| المجموعة | النتيجة |
|---|---|
| الهوية | **فشلت**: المعاملات ٤٢٧ بدل ٤٢٨، والسطور ١١٧٩ بدل ١١٨٣، ورأس السلسلة مختلف |
| السلامة | **نجحت كلها** — سلسلة متّسقة وميزان صفري، لأن معاملة متوازنة كاملة أُزيلت |

النتيجتان صورتان متعاكستان، وهما معاً الجواب على «لماذا مجموعتان»: **كلٌّ منهما
تكشف ما تعمى عنه الأخرى تماماً.**

## ٥. الاستعادة الحقيقية (لا تمريناً)

```bash
# ١. أوقف التطبيق. لا تستعيد تحت كتابة حيّة.
# ٢. تحقّق من سلامة النسخة قبل لمس أي شيء:
cd /srv/backups/<الطابع الزمني> && sha256sum --check SHA256SUMS

# ٣. الأدوار أولاً (على عنقود جديد):
psql "$ADMIN_URL" -f roles.sql

# ٤. قاعدة بيانات فارغة ثم الاستعادة:
psql "$ADMIN_URL" -c 'CREATE DATABASE engineering_marketplace;'
pg_restore --dbname="$DATABASE_SUPERUSER_URL" --no-owner --no-privileges \
           --jobs=4 database.dump

# ٥. لا تُشغّل التطبيق قبل أن يمرّ التمرين على ما استعدتَه:
npm run restore-drill -- /srv/backups/<الطابع الزمني>
npm run db:prove-rls
```

**لا تُعِد تشغيل التطبيق قبل الخطوة ٥.** استعادةٌ فقدت سياسة RLS تبدو سليمة
تماماً من الخارج، وتكون قد فتحت الدفاتر للجميع.

## ٦. سياسة النسخ الاحتياطي — قرار المالك (OPEN-10، محسوم)

| البند | القرار |
|---|---|
| **أين** | تخزين كائنات متوافق مع S3، **خارج خادم التطبيق**، ويُفضَّل عند مزوّد آخر |
| **كم نسخة** | نسخ تاريخية متعدّدة، والاحتفاظ يُضبط عند المزوّد لا في الكود |
| **التشفير** | AES-256-GCM قبل مغادرة الخادم. المزوّد لا يرى إلا نصّاً مشفَّراً |
| **من يملكها** | المالك وحده. بيانات اعتماد النسخ منفصلة تماماً عن بيانات التطبيق |
| **RPO** | **ساعة واحدة.** نسخة كاملة كل ساعة |
| **ملفات المنتجات** | تخزين كائنات منفصل وآمن، لا قرص الخادم — وهو الوضع القائم أصلاً |
| **الأسرار** | لا كلمة مرور ولا مفتاح في المستودع. متغيّرات بيئة فقط، ويحرسها اختبار |
| **الحذف** | حذف بيانات الموقع **لا يحذف** تاريخه. لا توجد عملية حذف بعيدة في أي سكربت |
| **تبديل المزوّد** | S3 واجهة قياسية: التبديل نقطة نهاية ومفتاح، لا إعادة بناء |

### الفصل ليس وعداً، بل بنية

كل متغيّرات النسخ الاحتياطي تبدأ بـ`BACKUP_`، و**لا واحد منها في**
`src/lib/config/env.ts`. الموقع العامل لا يتحقّق منها ولا يقرؤها ولا يملك
عميلاً لذلك الدلو. فموقعٌ مُخترَق لا يستطيع قراءة نسخة، ولا الكتابة فوقها، ولا
حذفها — **لأنه لا يملك المفتاح، لا لأن سياسة تمنعه**.

ويفشل `src/lib/security/backup-isolation.test.ts` في اللحظة التي يتغيّر فيها
ذلك. جُرِّب بزرع العيب: أُضيف `BACKUP_S3_BUCKET` إلى مخطط بيئة التطبيق وأُضيف
`DeleteObjectCommand` إلى سكربت الشحن، ففشلت أربعة فحوص، ثم عادت كلها خضراء
بإزالتهما.

### لماذا ساعة كاملة لا دقائق

نسخة كاملة كل ساعة، لا أرشفة WAL مستمرة. الأخيرة تعطي RPO بالدقائق لكنها تصميم
آخر بإجراء استعادة آخر، وأنت طلبتَ **ساعة**. وحجم القاعدة اليوم يجعل النسخة
الكاملة أقلّ من ميغابايت واحد مضغوطة، فالتكلفة الساعية لا تُذكر.

والدفتر **قيد مزدوج بسلسلة تجزئة**، فما يعنيه فقدان ساعة ليس بيانات مشوّهة بل
**فترة مفقودة بحدّ واضح**: رأس السلسلة في النسخة يحدّد بالضبط آخر قيد سليم.

إن لزم لاحقاً أقلّ من ساعة، فالطريق أرشفة WAL على مضيف القاعدة — وعندها يتغيّر
إجراء الاستعادة في §٥ كلياً، ولا يُفعَّل ذلك بتغيير رقم في cron.

### مفتاح التشفير — الخطر الحقيقي

`BACKUP_ENCRYPTION_KEY` هو الفارق بين نسخة ونفاية. **احفظه في مكان ثالث**: لا
على الخادم وحده ولا مع بيانات اعتماد الدلو. بلا هذا المفتاح لا تُفتح أي نسخة،
ولا توجد طريقة لاستخراجه — وهذا مقصود، وهو ما يجعل تسرّب الدلو غير مؤذٍ.

## ٧. الاحتفاظ المحلّي

النسخ على الخادم **منطقة عبور لا أرشيف**. الأرشيف هو الدلو، وهو ما يبقى بعد
فقدان هذه الآلة.

`BACKUP_LOCAL_KEEP` (الافتراضي ٢) عدد النسخ المحلّية التي يُبقيها
`backup:hourly`. اثنتان لا واحدة، حتى تبقى نسخة أمس على القرص إن فشل شحن اليوم.
و`BACKUP_RETAIN_DAYS` في `backup.sh` وحده يحذف بالعمر، ويضبطه `backup:hourly`
على `0` لأنه يتولّى العدّ بنفسه.

**ولا شيء من هذا يمسّ الدلو.** الاحتفاظ البعيد قواعد Object Lock وLifecycle
تضبطها أنت في لوحة المزوّد — حيث لا يصل هذا المستودع.

## ٨. الاستضافة المُدارة المجانية — قيدٌ مُثبت بالقياس

**المنصة تعمل على أي PostgreSQL مُدار يمنحك حساباً بصلاحية `CREATEROLE`** (وهو
شكل الحساب في Neon وSupabase وRailway وRender). جُرِّب فعلاً بحساب **ليس
superuser**:

| ما جُرِّب | النتيجة |
|---|---|
| إنشاء قاعدة البيانات | ✅ |
| إنشاء `app_user` بـ`NOBYPASSRLS` و`migrator` | ✅ |
| نقل ملكية `public` إلى `migrator` | ✅ بعد سطر إضافي واحد (أدناه) |
| `pgcrypto` و`citext` و`pg_trgm` | ✅ (موثوقة في PG13+) |
| **الترحيلات الـ٣٨ كاملة** | ✅ |
| **٧٠ سياسة صف، ٣١ جدولاً بـRLS، ٢٠ دالة SECURITY DEFINER** | ✅ مطابقة تماماً لقاعدة المرجع |
| `app_user` يحاول إنشاء جدول | ✅ رُفض: `permission denied for schema public` |

السطر الإضافي الوحيد اللازم على PostgreSQL 16، لأن حساباً بـ`CREATEROLE` وليس
superuser لا يستطيع منح الملكية لدور ليس عضواً فيه:

```sql
GRANT migrator TO <حسابك المُدار> WITH SET TRUE;
```

### لكن النسخ الاحتياطي **لا يعمل** هناك

```
pg_dump: error: query would be affected by row-level security policy
         for table "audit_logs"
```

**١٩ جدولاً في هذا المخطط يستعمل `FORCE ROW LEVEL SECURITY`**، وهو يسري على
**مالك الجدول نفسه**. لذلك `pg_dump` يرفض التصدير إلا لـsuperuser أو لدور
يحمل `BYPASSRLS` — وإنشاء أيٍّ منهما يحتاج superuser، وهو ما لا يمنحه مزوّد
مُدار. جُرِّب ثلاث مرات: بالحساب المُدار، وبنفس الحساب مع إعلان دور المالك عبر
`PGOPTIONS`، وبمالك الجداول `migrator` نفسه — **فشل في الثلاث**.

`pg_dumpall --globals-only --no-role-passwords` يعمل بلا superuser، فالمشكلة
في القاعدة لا في الأدوار.

### ماذا يعني هذا عملياً

| الخيار | الترحيلات والتشغيل | `npm run backup` وتمرين الاستعادة |
|---|---|---|
| PostgreSQL في حاوية على خادمك (`docker-compose.prod.yml`) | ✅ | ✅ يعمل كما هو مُختبَر |
| PostgreSQL مُدار مجاني | ✅ | ❌ لقطات المزوّد فقط |

**وهذا يرجّح الخادم الخاص لهذه المنصة تحديداً**، لأن الدفتر هو السجل التجاري:
النسخة التي أستطيع إثبات سلامتها — بمطابقة رأس سلسلة التجزئة وإعادة التحقق من
كل قيد — لا يمكن أخذها أصلاً على قاعدة مُدارة. ولو اخترت المُدار فاعتمد لقطات
المزوّد، **وجرّب استعادة واحدة فعلياً قبل أول عملية بيع حقيقية** — لقطة لم
تُستعد ليست نسخة احتياطية.

## ٩. التشغيل الفعلي — الأوامر

```bash
# كل ساعة، من cron. أمر واحد: نسخة، تشفير، شحن، تسجيل.
0 * * * * cd /srv/enginora && npm run backup:hourly >> /var/log/enginora-backup.log 2>&1
```

`backup:hourly` يخرج بحالة غير صفرية عند أي فشل، **ليراسلك cron**. مهمّة نسخ
تفشل بصمت أسوأ من غياب المهمّة: تنتج الاعتقاد بوجود نسخ.

### الاستعادة من نسخة مشحونة

```bash
npm run backup:fetch -- 20260914T084659Z      # ينزّل ويفكّ التشفير ويطابق البصمات
npm run restore-drill -- ./restored/20260914T084659Z
```

`backup:fetch` يطابق `SHA256SUMS` **المأخوذة قبل التشفير**، فتطابقها يثبت أن
التشفير والرفع والتنزيل وفكّ التشفير كانت كلها بلا فقد.

### التمرين الدوري

نجاح التمرين يكتب `backups/.state/last-drill`، و`backup:hourly` يقرؤه ويشتكي
بعد `BACKUP_DRILL_DUE_DAYS` (٣٠ يوماً افتراضاً). **الفشل لا يكتب التاريخ** — فلا
يُعاد ضبط الساعة بتمرين فاشل.

**التوصية: تمرين شهري يسبق التسوية**، لأن أسوأ لحظة لاكتشاف نسخة لا تُستعاد هي
لحظة الحاجة إليها.

### ما جُرِّب فعلاً، لا ما وُصف

الحلقة كاملة شُغِّلت على قاعدة بيانات حقيقية وتخزين حقيقي بروتوكولاً:

```
قاعدة حيّة → backup.sh → تشفير → شحن (٤ قطع، قُرئت بعد الرفع)
          → جلب → فكّ تشفير → مطابقة SHA256SUMS → استعادة
          → ٢٢ فحصاً، منها رأس سلسلة التجزئة: 46114150577df630…
DRILL PASSED
```

وجُرِّب الرفض أيضاً: الجلب بمفتاح خاطئ **يُرفض**، ويطبع سبباً مقروءاً بدل أثر
نداءات Node — وهو ما اكتُشف بتشغيله بمفتاح خاطئ والنظر إلى ما خرج.
